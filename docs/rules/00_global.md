# 全ページ共通ルール

## 目的

全画面に共通する現在の正しいルールをまとめる。

画面別の細かい業務ルールは、このファイルに増やさず、対象フォルダのdocsへ分ける。

## プロジェクトフォルダ固定ルール

- このプロジェクトの作業対象は C:\dev\tcpg_system_laravel の中だけ。
- 一時パッチ、一時スクリプト、調査用ファイルも C:\dev\tcpg_system_laravel の中にだけ作る。
- C:\dev\pc_mini_toolbar など別システムのフォルダを、Laravel作業の一時置き場にしない。
- 別フォルダを読む、書く、削除する必要がある場合は、作業前に対象パスと理由を出して確認する。

- 一時ファイルが必要な場合は C:\dev\tcpg_system_laravel\_tmp_codex に集約する。
- _tmp_codex はCodex作業用の一時フォルダとし、作業終了時に中身を確認して削除可否を報告する。
- C:\tmp や別プロジェクトフォルダを一時置き場にしない。

## 一時スクリプト

### 許可

以下はユーザーへの確認不要。

- 1回限りの一時スクリプト
- 実行後に自動削除する一時ファイル
- デバッグ用コード
- 一時SQL
- 一時ログ出力

これらはAIの判断で作成・実行・削除してよい。ただし、一時ファイルは必ず C:\dev\tcpg_system_laravel\_tmp_codex に置く。

### 要確認

以下は必ずユーザーへ確認する。

- 新規ファイルの追加
- 永続的なファイルの追加
- 新しいフォルダの作成
- ライブラリ追加
- composer変更
- DB構造変更
- Migration追加

### 優先順位

1. 直接修正
2. 一時スクリプト
3. ユーザーへ確認

AIは1→2→3の順で判断する。

## 基本方針

- 日本語の表示、ラベル、説明文を壊さない。
- 一括置換で日本語や画面構造を直さない。
- 変更は1つずつ、対象範囲を絞って行う。
- 余計なついで修正をしない。
- 既に動いているもの、Accessと一致確認済みのものを理由なく変えない。
- 推測で計算式、表示名、DBカラムを変えない。

## 作業前に確認すること

- どの画面の問題か。
- どの年月、どのスタッフ、どの店舗、どのボタンで起きたか。
- DB保存値が違うのか、画面表示だけが違うのか。
- 帳票だけの問題か、保存処理まで影響しているか。
- 対象ページの `docs/rules/{対象}/` があるか。

## データと表示のルール

- 帳票は原則としてDBの保存値を表示する。
- 帳票側で勝手に再計算しない。
- 表示だけの修正でDB値を変更しない。
- DB値が正しい場合はView側、渡し方、表示整形を確認する。
- DB値が違う場合はControllerより先にServiceの保存処理を確認する。
- 確認用、仮、概算の数字を通常の値として画面に出さない。
- 2026年8月、給与の差引支給額（`supply_deduction_sum`）で実例あり：保存処理を経由せず
  表示のたびに正本Serviceの計算メソッドをライブ呼び出しする形に、誰にも確認されないまま
  変わっていた。DB列は古いまま（ある時期以降ずっと0）で、画面はライブ計算した値を出して
  いたため、誰も気づかなかった。保存処理（再計算・確定のタイミング）で計算し、DBへ保存し、
  表示側は保存値を読むだけにする形へ戻した。「正本のメソッドがある」ことと「そのメソッドの
  結果がちゃんとDBに保存されている」ことは別。正本メソッドを表示側から直接呼んでいないか、
  呼んでいる場合はそれが保存目的なのか表示目的なのかを都度確認する。

## 計算のルール

- 同じ意味の計算式を複数作らない。
- 給与、賞与、勤怠、売上などで共通化できる計算はServiceへ寄せる。
- ただし、無理な共通化で業務ルールが読みにくくなる場合は分ける。
- 法改定や料率変更がある計算は、計算根拠をdocsへ残す。
- ボタンを複数回押すと結果が変わる状態にしない。
- 税額・控除額など国税庁等が年度ごとに金額表を公開している計算は、AIの一般知識や記憶だけで
  数字を決めない。必ず公式サイトの該当年度の一次資料で数字を確認し、既存の確定済みデータと
  突き合わせて検証してから実装する（2025年8月、年末調整の基礎控除・配偶者控除・給与所得控除の
  丸めで実例あり。詳細は `docs/rules/year_end_adjustment/03_calculation.md`）。
- 法改正・料率改定があっても対応できるように、計算ロジックは1箇所（正本のService）にまとめる。
  ロジックが変わったとき、その1箇所を直せば全ての画面・帳票へ反映される状態を保つ。
  年度で計算式が変わる場合は、Service内でtargetYear等により分岐する形に統一し、
  給与・PDF帳票側などに同じ計算のコピーを作らない。

## エラー処理のルール

- テーブル名・カラム名が存在しない、接続できない等の**本来起きてはいけないエラー**を
  `try { ... } catch (\Throwable) { return []; }`のような形で握りつぶし、空配列や`false`、
  `null`にフォールバックして処理を続けない。握りつぶすと、テーブル名を間違えた瞬間に出るはずの
  例外が消え、コード修正時に気づく機会を失う。
- 区別すること：「この会社にはまだマスタの行が0件」のような**正常な空データ**は、
  フォールバックではなく単なる空の結果として扱ってよい。禁止しているのは「クエリ・スキーマ
  確認そのものが失敗した」場合に例外を隠すこと。
- 2026年8月、実際にあった事故：`StaffPortal\PayrollController`が手当名マスタを`t_allowance`
  という存在しないテーブル名で参照していたが、複数箇所で例外を`catch (\Throwable)`により
  空扱いにしていたため、会社ごとの手当名カスタマイズ機能が何ヶ月も静かに無効化されたまま
  誰も気づかなかった。同じ日に同種の握りつぶしが認証・Master・Report系のServiceにも
  13箇所見つかり、全て削除した（詳細は`docs/rules/payroll_bonus/99_do_not_touch.md`）。
- コードレビュー・調査時は、DB/スキーマ呼び出しを囲む`catch (\Throwable)`（または広すぎる
  catch）を見つけたら、この握りつぶしパターンでないか必ず確認する。
- リクエストの入力値は必ずフィールド名（`$request->input('列名')`等）で受け取る。
  `array_values($request->except([...]))`のように送信順（配列の位置）へ変換してから
  分割代入しない。フォーム側のinput順序が変わると、気づかず違う値が違う項目に入る
  （2026年8月、勤怠編集フォームで実例あり。残業時間や備考が意図しない項目に入る
  危険な状態だった）。
- フォームのバリデーションで許可する文字数（`max:`）は、必ず実際のDBカラム長に合わせる。
  DBより緩い上限にすると、バリデーションを通過した後の保存処理で初めて生のSQLエラー
  （文字列の切り捨て）になり、どの入力が原因か画面からは分からない。特にCSV取込など
  Laravelのバリデーションを経由しない書き込み経路は、行番号・列・値を明示したチェックを
  自前で入れる（2026年8月、レセ関連の複数フォームで実例あり）。
- 名前が似ている複数のDBカラム（例: 用途の異なる2つの「患者名」カラム）がある場合、
  名前の類推だけでどちらを使うか決めない。実際のテーブル定義と、他の機能がどちらへ
  保存しているかを確認してから参照する。

## 管理側とスタッフ側の一致

- 同じデータに対する計算式・表示ロジックは、管理側とスタッフ側で必ず同じにする。
  スタッフ側だけ別の計算を実装しない。
- スタッフ側で「表示しない項目がある」のは構わない（表示制御で隠すだけ）が、
  表示する項目の計算結果そのものが管理側と違う値になってはいけない。
- 確定済み（給与確定、勤怠確定など業務上の「確定」）のデータは、確定後はスタッフ側から
  編集できないようにする。管理側で確定解除するまで、スタッフ側の編集経路を塞ぐこと。
- 2026年8月、勤怠機能の調査で「管理側・スタッフ月間・スタッフ側管理詳細の3画面で
  変更実績所定時間の解決ロジックが別々に実装され、管理側の編集内容が一部の画面に
  反映されない」という実例が見つかった。新しい画面・APIを追加するときは、既存の
  正本Service（例: 勤怠の`AttendanceV2MonthlySummaryService`）を必ず経由し、
  Controller/Blade側で同じ計算をもう一度書かない。

## 過去データの保護

- 確定済み（給与確定・勤怠確定・年調処理済みロックなど）のデータは、理由なく再計算・上書きしない。
- 再計算や一括処理を作るときは、対象の確定状態を必ずチェックし、確定済みなら処理をスキップする
  （チェックを忘れると、UIやAPIを直接叩かれた場合に確定済みデータが書き換わってしまう）。
- 法改正・計算式の修正を行っても、過去に確定・保存された金額は変えない。新しい計算式は
  未確定のデータ、または今後新しく計算するデータにだけ適用する。

## コードの見つけやすさ

- 計算ロジック、PDF・帳票の座標/レイアウト、フォーム/CRUD処理は、意味のある単位でファイルを分ける
  （例: `YearEndCalculationService`のように計算だけを別Serviceへ切り出す）。
  1つのControllerに全部書き込んで巨大化させない。
- 分けたファイルの先頭には、そのファイルが何を担当するか（計算だけ／PDF座標だけ、など）を
  コメントで明記する。呼び出し元をたどらなくても「ここに何があるか」が分かるようにする。
- 変数名・メソッド名から意図が読み取れない省略や、文字化けした文字列リテラルをコード中に残さない。
  文字化けに気づいた場合は、実データ（DBの実際の値）と突き合わせて正しい値を確認してから直す。
  存在しない値に一致するよう「それらしく」直さない（2026年8月、給与計算の部署名判定で
  文字化けにより除外ロジックが機能していなかった実例と、実在しない部署名を条件に使っていた
  実例の両方が見つかった）。

## 保存処理のルール

- 保存ボタンは、ユーザーが手入力した値を消さない。
- 保存ボタンでマスタ値を勝手に再取込しない。
- 手入力欄を更新する処理は、対象ボタンと対象項目を明確にする。
- 確定済みデータを更新する場合は、確定解除や確認メッセージなど既存の業務ルールに従う。

## DBカラムのルール

- 使わない可能性があるカラムはいきなり削除しない。
- 退避する場合は先頭に `x_` を付ける。
- コード内で参照がないことを確認してから、実運用後に削除を検討する。
- `old` が付くカラムは原則として整理候補。ただし、使われている可能性があれば先に確認する。
- ラベル変更だけで済む場合はDBカラム名を変えない。

## 画面構成のルール

- 管理画面とスタッフポータルは分けて考える。
- 共通フレーム、共通ヘッダー、共通CSSを勝手に混ぜない。
- 通常ページは、対象フォルダの `index.blade.php` を中心に読める構成にする。
- 細かいBlade分割を増やしすぎない。
- 共通部品を触る時は、使っている全ページに影響する前提で確認する。

## CSSのルール

- 管理画面共通は `public/css/admin_v2/`。
- スタッフポータル共通は `public/css/staff_portal/`。
- 全ページ共通の見た目は共通CSSへ置く。
- そのページだけの見た目はページ側に置いてよい。
- 同じCSSを複数ページで使い始めたら共通化を検討する。

## ルート・Controller・Serviceのルール

- Routeは業務単位でまとめる。
- Controllerは業務単位を基本にする。
- Controllerに長い計算ロジックを書かない。
- 計算、集計、保存ルールはServiceへ寄せる。
- Traitは最後の手段。最初からTraitへ逃がさない。

## ファイル整理のルール

- `zzz_` は未使用確認済み、または削除候補として扱う。
- `zzz_` にしたファイルを同時に元名でも残さない。
- 一時スクリプト、調査用ファイル、生成キャッシュはコミットしない。
- `storage/framework/views` のコンパイル済みビューはコミットしない。

## ドキュメント更新のルール

- 全ページ共通ルールはこのファイルへ書く。
- ページ別の細かいルールは対象フォルダへ書く。
- 間違っていたルールは正しい内容へ上書きする。
- 間違ったルールを本文に残さない。
- 変更理由や判断経緯だけを `change_log` に短く残す。

## 迷った時の停止条件

以下に当てはまる場合は、変更前に止まって確認する。

- どのDBカラムが正しいかわからない。
- Access時代の計算とLaravelの計算が違う。
- 表示値とDB保存値が違う。
- どのページに影響するかわからない。
- 日本語が文字化けしている。
- 旧コード、旧カラム、`old`、`x_` を使う必要があるように見える。
- 画面上は直せそうだが、保存値も変わる可能性がある。
- DB/スキーマ確認が`try/catch`で握りつぶされていて、失敗時の挙動が読み取れない。
- リクエストの値を配列の位置（送信順）で受け取っている箇所がある。
