# 仕訳帳 変更履歴

## 2026-08-23 保存・削除の確認漏れ修正（仕訳帳・請求書）

`AccountingV2Controller`の`updateJournalEntry()`/`updateJournalEntryGroup()`/`deleteJournalEntry()`が、
対象`journal_entry_id`の実在確認・`update()`/`delete()`の影響行数チェックをせず、常に
「仕訳帳を保存/削除しました。」と表示していた（041実運用の監査を機に管理側も横断監査）。
影響行数が0件ならerrorMessageを返すよう修正。`updateJournalEntryGroup()`は複数行を
1トランザクションで更新するため、1行でも0件だった場合は例外を投げてロールバックし、
部分的にだけ保存された状態を作らないようにした。

`applyJournalEntriesReview()`（CSV取込の確認画面適用）は、確認内容を最大60分`Cache`に
保持したまま適用するため、その間に対象仕訳が他で編集・削除されると更新/削除が0件で
空振りする可能性がある。影響行数を見て、空振りした仕訳をID付きで結果メッセージに
「確認時から状態が変わり反映できなかった仕訳」として明示するよう修正（黙って
`$updatedCount`/`$deletedCount`に数えない）。

同じタイミングで`BillingListV2Service`（請求書、`app/Http/Controllers/Admin/V2/BillingListV2Controller.php`）の
`updateInvoice()`/`deleteInvoice()`/`updateDetail()`/`deleteDetail()`にも同型のバグがあり、
影響行数を返すよう変更してコントローラー側で0件ならエラーメッセージを出すよう修正。

## 2026-08-15〜18 仕訳帳CSV取込の作り直し

`AccountingV2Controller::importJournalEntries`(仕訳帳CSV取込、`/admin/work/journal-entries`)を2026-08-15に大きく作り直した。「不可逆な削除・上書きは機械に最終判断させず、検知・提示までにとどめ人が選んで適用」の方針に基づく。

**背景:** 元はcodex実装で、CSVの列(会社+日付+仕訳No+借方/貸方の内容まるごと)が完全一致しないと「更新」と認識されず、内容が変わった仕訳(不明→確定の再分類、単仕訳→複合仕訳への変化)が新規行として二重に入り、古い行が孤児化する問題があった。また`allocation_ratio`(分割割合、さくら報酬計算専用・CSVには存在しない列)がCSV再取込のたびに空文字で上書きされて消える実バグもあった。

**設計:**
- 会社＋取引日＋仕訳No(`journal_breakdown`)でグループ化し、DBに同じグループが無ければ新規として即取込
- 既存グループがある場合は自動更新せず、`/work/journal-entries/import/review/{token}`の確認画面で既存内容とCSV内容を明細ごと並べて表示し、仕訳Noごとにチェックを入れたものだけ適用
- 適用時は既存行とCSV行を出現順で対応づけてUPDATE(`journal_entry_id`を維持)。`received_amount`/`is_confirmation_checked`/`deposit_confirmation_note`(`PaymentConfirmationController`が使う入金確認データ)や`allocation_ratio`はCSV取込が一切触らない
- 既存行がCSV行より多く余った場合、これらの手動項目に値が入っていれば削除せず結果メッセージで名指しして報告、何も入っていなければ削除
- 取込のたびに「科目別照合表」(借方/貸方の勘定科目ごとにCSV合計とDB合計を突き合わせ)を必ず表示。取込むものが無いCSVでも照合だけ確認できる用途に使える
- ステージング用データは`Cache`(`journal_import_review:{token}`、60分TTL)に保持。新規テーブルは作らない

**2026-08-18の追加改修:**
- **2段階化**: アップロード時点では一切書き込まず、確認画面で「新規追加候補N件」を見せてから別ボタン(`applyNewJournalEntries`)を押した時だけ実INSERTする流れに変更。一致確認(科目別照合)も新規追加が終わった後(DBが正しい状態になってから)だけ計算・表示する。
- **要確認の判定を絞った**: `REVIEW_COMPARE_FIELDS`(借方/貸方科目・金額のみ)で一致判定。摘要・部門名・税区分・メモ・管理番号は対象外(摘要の表記ゆれ、部門名はマッピング元マスタ変化で毎回「不一致」になってしまうため)。これをやる前は些細な差分が数百件単位で埋もれて実質使い物にならなかった。
- **複合仕訳の行対応バグ**: 既存行とCSV行を単純に出現順(0番目同士...)で対応づけていたため、DB保存順とCSV行順が違うだけで全行「差分あり」に見えていた。中身が完全一致する行同士を先に対応づけてから余りだけ突き合わせる方式に修正(`buildReviewLinePairs`)。**`applyJournalEntriesReview`側の実適用ロジックはまだ旧方式(出現順の位置合わせ)のまま——表示は直ったが適用時に対応がズレる可能性が残っている。既存が2行以上の複合仕訳をチェックして適用する前は要注意。**
- **重大NULLバグ**: 一致確認の除外条件`whereNotIn('credit_account_title', [...])`が、該当列がNULLの行(借方だけの片側仕訳、銀行利息など)をSQLの三値論理で丸ごと除外し、実際は一致してるのに不一致表示になっていた。`whereNull(...)->orWhereNotIn(...)`で修正済み。
- **N+1パフォーマンス問題**: 新規/要確認判定を仕訳グループ(数百〜数千件)ごとに毎回DBへ問い合わせていて、数ヶ月分の範囲だと実行時間60秒を超えFatal Errorになっていた。対象期間・会社のデータを最初に1回だけ取得しメモリ上で引く方式に修正。
- 一覧画面(`journal_entries/index.blade.php`)にページング追加: グループ数が1000件超だとブラウザが固まっていた。全クリアボタンも追加(期間・会社含め全項目リセット)。
- 完了メッセージの内訳(新規追加候補／要確認／既存と完全一致／対象期間外・除外科目等)を漏れなく表示するよう修正。完全一致件数が集計されてるのに表示から漏れていた。

**未着手:** 回帰防止テストが無いので、実CSVでの動作確認とテスト追加が望ましい。入金確認済み単仕訳は複合仕訳に変化しない・確認後に仕訳内容が変わらない、という業務前提のもとで設計している。上記の複合仕訳の行対応バグ(適用ロジック側)も未修正のまま。
