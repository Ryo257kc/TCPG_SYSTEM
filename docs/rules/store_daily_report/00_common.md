# 店舗日報 共通ルール

## 対象画面

- /staff/office/store_daily_report
- /staff/office/store_daily_report/daily_summary
- /staff/office/store_daily_report/daily_summary/detail
- /staff/office/store_daily_report/request_history
- /staff/office/store_daily_report/return_note
- /staff/office/store_daily_report/other_list
- /staff/office/store_daily_report/item_summary

## 基本方針

- 店舗日報は、月間日報、月報、月次処理、売上仕訳に連動する。
- 表示側で売上を勝手に再計算しない。正しい数字は月間日報で集計し、月次テーブルへ保存し、その数字を仕訳へ反映する。
- 売上一覧や売上PDFは仕訳を表示するだけ。店舗日報側と別ロジックで数字を合わせない。
- 月次済みのデータは編集不可。変更が必要な場合は月次解除してから編集する。
- 店舗未選択時は、店舗別に確認する帳票や印刷を無理に出さない。

## 月次の流れ

1. 月間日報で正しい集計数字を確認する。
2. レセ負担金のさくら、ひなた分を入力する。
3. 保険負担は月間日報から自動集計する。
4. 保存後、月次確定で mx_monthly_closings に確定値を保存する。
5. 月次確定時に mx_journal_entries へ売上仕訳を作成する。

## 金額ルール

- レセ負担金の下枠は、mx_monthly_closings の保存値を使う。
- 保険負担は月間日報の集計値。入力欄ではなく自動表示。
- 店舗経費は月間日報の集計に含める。
- 月間日報と売上一覧の数字が違う場合、売上一覧で補正せず、月次テーブルと仕訳作成元を確認する。

## 禁止

- Accessで一致確認済みの集計条件を、確認なしに変更しない。
- 月間日報と月報を同じ帳票扱いにしない。別PDFとして扱う。
- 月次解除時に、関係ない往診月次やレセ月次の仕訳を削除しない。
- 仕訳表示側で店舗日報の数字を再計算しない。
- 店舗日報権限をダッシュボード表示条件に使わない。ダッシュボード上は事務所メニュー配下に置く。

## 保存の確認（2026-08-23、サイレント失敗の一斉修正）

`StoreDailyReportController`の保存系メソッドが、対象行の実在確認や`update()`の影響行数を
一切見ずに、常に「保存しました。」を返していた（041の実運用でこのパターンの不具合が
複数見つかったことを受けて全保存系メソッドを監査）。DEVは店舗日報テーブルに関しては
開発専用で本番移行時にテーブルごと切り替わるため、この時点でまとめて修正した。

- `saveDailySummaryDetail()`：`T_患者名日報`の実在確認を保存前に追加。`T_先生別日報`の
  `update()`が0件なら`\RuntimeException`を投げ、呼び出し元でerrorMessageに変換する構成に変更。
- `saveReturnNote()`（返戻ノート）・`saveRequestHistory()`（依頼履歴）：`update()`の影響行数を
  見て、0件ならerrorMessageを返すよう修正。
- `saveDailySummaryExpense()`（経費行）：`T_レジ詳細`の`update()`/`delete()`が0件の行があれば
  即エラーで返すよう修正。以前は対象行が見つからなくても`$savedCount`が無条件で加算され、
  金額編集が実際には保存されていないのに「経費を保存しました。」と表示されていた
  （このパターンが一番実害が大きい）。
- `bulkCheckDailySummaryDetail()`（一括ch更新）：影響件数をメッセージに含め、0件なら
  「更新対象がありませんでした。」と表示するよう修正（一括処理の性質上エラー扱いにはしない）。

**How to apply**: この控えめ機能追加パターン（対象実在チェック＋`update()`/`delete()`戻り値の
影響行数チェック）は、店舗日報のこのコントローラーに限らず、StaffPortal側で新しい保存処理を
書くとき・既存の保存処理を触るときは必ず確認する。0件更新を成功として返さない。

## 割合の選択肢はT_割合マスタから引く（2026-09-05修正）

`daily_summary/detail.blade.php`の「割合」`<select>`は、専用マスタ`dbo.T_割合`
（0/1/2/3/原/交/子/自/障/水/乳/母、`No`列で表示順を持つ）があるのに使わず、
「その日表示中の患者summaryに実際に出てきた値」だけから選択肢を作っていた。
使用頻度の低い区分（交・母等）はその日に該当患者がいないと選べず、日によって
選択肢の数が変わって見えていた（店舗からの問い合わせで発覚）。
`StoreDailyReportController`で`T_割合`から`No`順に取得し`ratioOptions`として渡す形に修正、
blade側の「その日の実績から作る」ローカル集計は削除した。

## 日報印刷の誤差表示の調査（2026-09-05・コード修正なし、DEVデータの問題と判明）

店舗から「日報印刷の売上欄に誤差が出るが実際には合っている」との報告（7/3・7/29さくら）。

調査の過程で`print.blade.php`の`$bankDepositAmount`計算式（`$dailySalesAmount -
$chargeUseTotal + $chargeDepositTotal`、チャージ入金分を足す形）を「チャージ入金分は
店舗が預かってるだけで銀行にまだ入ってないはずだから足すのはおかしい」という仮説のもと、
旧AccessのF_日別日報フォームの誤差チェック式（自費計+保険負担計-レジ控除-カード合計+
チャージ残金）を分解し、`T_日報集計.チャージ残金`列の実データ（7/3:-26520, 7/29:-14750）が
「-本日チャージ使用分」と完全一致することから「チャージ入金分は式に不要」と判断して
一度コードを変更した。

**しかし誤りだった。** ユーザーが実際のAccessフォーム・印刷画面のスクリーンショットを
提示（7/3、さくら）したところ、正式な銀行預入金額は**77,370円**、誤差チェックは
**0（正常）**と表示されていた。これは現行コード（変更前）の計算式がそのまま計算する値と
完全一致する。つまり**元の計算式は最初から正しく、コードにバグは無かった。**

一方、DEV DB（`T_日報集計.銀行預入金額`）に入っていた値は**44,550円**で、本来の77,370円と
全く違う。今回の「誤差」はコードの計算ミスではなく、**DEVデータベースのこのレコードの
銀行預入金額が、実際の値と一致していない**ことが原因。コードの変更は全て元に戻し済み
（`print.blade.php`のこの箇所は無変更）。

**教訓**: 店舗日報系のDEVデータで実データ検証する時は、計算結果とDEVの保存値を比べて
「一致しない＝コードのバグ」と即断しない。DEV側のデータ自体が本番と食い違っている
可能性を先に疑うこと。特に日報系はDEV/本番同期の実態が他ドメインほど検証されていない
（他ドメイン（仕訳）でも同様のDEV独自不整合が過去に見つかっている、経緯はメモリ
`project_journal_entries_dev_duplicates`参照）。

「担当者」`<select>`（`dailySummaryDetailOptions.staffOptions`）も同じ「実際に使われた
値だけ」パターンで作られていた。こちらは`mx_staffs.front_staff`（施術担当権限、
権限画面では「店舗システム」表示）で絞る設計だったと判明。全期間で`T_先生別日報`に
実際に登場した担当者IDが`front_staff=1`の集合に完全一致することを確認済み。
`front_staff=1`で`mx_staffs`から取得し`staffOptions`として渡す形に修正、店舗による
絞り込みは行っていない（全店舗の施術担当スタッフを表示）。

在職/退職の判定は`employment`（現在の状態フラグ）ではなく`tai_date`（退職日）と
編集対象日（`targetDate`）を比較する形にした。日報は過去日付を編集することがあり、
「現在は退職済み」でも在籍していた期間の日付では引き続き選べる必要があるため
（ユーザー指摘、2026-09-05）。`tai_date IS NULL OR tai_date >= targetDate`。

既存行（サーバー描画時点）で担当者IDがこの選択肢集合に無い場合（対象日より後に
退職した担当者が入っている等）、その行の選択肢へその担当者だけ個別に追加する
セーフガードも追加済み。追加しないと`<select>`が「未選択」に見え、他項目だけ直して
保存した時に担当者IDが黙って空欄で上書きされる危険があった。
