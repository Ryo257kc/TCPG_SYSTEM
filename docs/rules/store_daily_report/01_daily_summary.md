# 月間日報 ルール

## 対象

- /staff/office/store_daily_report/daily_summary
- StoreDailyReportController::dailySummary()
- StoreDailyReportController::buildMonthlyWindowPrintData()

## 役割

月間日報は店舗日報の正しい売上集計を確認する正本。
売上一覧や売上PDFで別計算して合わせない。

## 集計元

- 患者別: dbo.T_患者名日報
- 先生別: dbo.T_先生別日報
- 経費: dbo.T_レジ詳細
- 差額: dbo.T_日報集計
- 月次保存値: dbo.mx_monthly_closings

## 基本式

通常分は patient.日付 で対象月を判定する。
回収分は patient.回収日 で対象月を判定し、patient.保険証 = 2 を対象にする。

- 自費: teacher.自費。ただし teacher.ch = 0。
- 保険負担: patient.レセ負担金（負担金ch = 0の分）＋ teacher.メニュー=返金の teacher.保険負担（現金返金分の調整）。
- その他/経費: T_レジ詳細。ただしチャージ金、物品販売、非表示ch は除外。
- 合計: 自費 + 保険負担 - その他。
- 差額: T_日報集計.差額。

### 返金（現金で窓口に返した分）

窓口で現金返金した場合、`T_先生別日報`にメニュー=「返金」・保険負担=マイナス値として記録されるが、
`T_患者名日報.レセ負担金`（受付側の値）は更新されない運用になっている。月間日報の保険負担計は
`patient.レセ負担金`が正本だが、この返金だけは先生別側にしか存在しないため、`メニュー=返金`の
行を別途SUMして加算（＝実質減算）する（2026-08-18、7/17さくらで保険負担が4,400円多く出る
不具合で発覚）。`T_日報集計.レジ`（レジ実額）はこの返金を差し引いた額と一致することを確認済み
（現金の払い戻しなので）。
返金以外でteacher.保険負担がマイナスの行（1,600件超）は対象にしない。それらは通常の請求調整で、
patient.レセ負担金側に既に反映されている前提。

**2026-08-20追記**：この調整は`buildMonthlyWindowPrintData()`（月次印刷）にしか入っておらず、
`dailySummary()`が呼ぶ`dailySummaryMonthlyWindowInsuranceTotals()`（月間日報一覧ページ上部の
月次締め入力欄、`sakura_insurance_burden_total`/`hinata_insurance_burden_total`）には
同じ調整が漏れていて、返金分が保険負担合計に残ったままになっていた（ユーザー報告により発覚）。
`dailySummaryMonthlyWindowInsuranceTotals()`にも同じ返金SUMを追加して修正。2026年7月さくらの
実データで確認：さくらの保険負担合計が返金-4,400円分だけ正しく減った（554,010円）。
**同じ調整が複数箇所に必要な計算は、今後1箇所に共通化するか、修正時に他の集計箇所も
grepで洗い出すこと**（`COALESCE(patient.レセ負担金`で検索すると該当箇所が見つかる）。

## レセ負担金

月間日報入力で手入力するのは、さくら・ひなたのレセ負担金のみ。
月次済みは mx_monthly_closings の保存値を表示する。
保険負担は月間日報の集計値で、自動表示。手入力欄として扱わない。

## 日報印刷

/staff/office/store_daily_report/daily_summary/print (`dailySummaryPrint()`)。

**大原則：通常日報と修正日報は計算が別物**。共通ロジックにまとめようとすると一生Accessと合わない
（2026-08-18、実際に何度もやり直した）。触るときは必ず`$isModifiedPrint`で完全に分岐させ、
通常日報・修正日報それぞれ単独でAccessと突き合わせて確認すること。2026/7/10さくら鍼灸整骨院で
両方フル一致確認済み（このセッションの検証データ）。

- 通常日報: teacher.計算外 = 0。teacher.ch は見ない。
- 修正日報: teacher.計算外 = 0、teacher.ch = 0（自費計算のみ。他の集計は下記）。
- 先生別外: 自費治療金、本日売上金、窓口合計からは除外しない。先生別集計から外すための条件。

2026/02/27 さくら鍼灸整骨院で一致確認済み。
- 通常日報 自費治療金: 59,610円
- 修正日報 自費治療金: 12,400円

### レセ負担金列：保険証忘れの扱いが通常日報と修正日報で違う

保険証忘れ（保険証=1/2）は施術はしても保険証を持ってきてもらうまで受付上の売上が立たない。

- **通常日報**：`patient.レセ負担金`の生値をそのまま表示（保険証忘れでも実際に入ってる値を出す）。
- **修正日報**：保険証忘れの行は施術日には0円、保険証を持ってきた回収日の行（UNION後に
  判別できるよう追加した`is_collection_row`マーカーで判定）でだけ実額を表示する。

2026/7/10さくら鍼灸整骨院で実測：通常日報の合計26,050円（秋富さんの1,220円を含む）、
修正日報の合計24,830円（秋富さんの行は0円）、どちらもAccessと一致確認済み（2026-08-18）。

### 保険負担列：通常日報・修正日報で条件を変えない

保険負担は`teacher.保険負担`のCASE集計（`copaymentSql`）そのままで、`isModifiedPrint`による
分岐は無い。一時的に「修正日報だけレセ負担金と同額にする」という誤った修正を入れたが、
ユーザー確認の結果撤回した（保険負担は日報と修正日報で変わらない。変わるのはレセ負担金と自費だけ）。

### 保険証忘れは来院人数・保険人数からも除外——ただし通常日報は除外しない

`dailySummaryPeopleRow`（来院人数・保険人数・自費人数等の集計）も通常日報と修正日報で条件が違う。

- **来院人数**：通常日報は`先生別外=0`のみ（保険証忘れも含む）。修正日報は
  `先生別外=0 AND 保険証=0`（保険証忘れを除外）。2026/7/10さくらで実測：通常64・修正63。
- **保険人数**：SQL側のCASE(`(請求金額+保険負担)<>0`)はAccessの通常日報クエリと同じで
  条件分岐しない。表示側で「SQL集計値 − 保険証忘れの人数」を引いた値を出す（通常日報・
  修正日報どちらも同じ計算。2026-08-18ユーザー確認）。2026/7/10さくらで実測：61−1=60
  （通常・修正とも60）。
- **自費人数**：`割合='自'`のみ（通常日報）／`割合='自' AND ch=0`（修正日報）。この条件分岐は
  元から存在していた。2026/7/10さくらで実測：通常3・修正2。当初「Accessは2人なのに3人いる」と
  思っていたのは、通常日報の値を修正日報のAccess参照と比較していた検証ミスだった。

「来院人数 = 自費人数 + 保険人数 + 保険証忘れ」が通常日報・修正日報どちらでも成立する
（検算式として使える。例：修正日報 2+60+1=63）。

**ブレード側の別バグ**：`print.blade.php`の`$displayVisitCount`が、修正日報の来院人数を
コントローラーの計算値を使わず独自に`自費人数+保険人数`で再計算していて、`保険証忘れ`の
加算を忘れていた（2+60=62、正しくは63）。コントローラー側をいくら直しても表示に反映されない
不具合の原因だった。`+保険証忘れ`を追加して修正（2026-08-18）。

### 修正日報から除外する行の条件

修正☑(`ch=1`)が付いていても、自費計・保険負担計・請求金額計・レセ負担金のどれか1つでも
金額が残っていれば「確認すべきものが残っている」とみなし修正日報に残す。**4項目全部が0円に
なって初めて除外する**（2026-08-18、ユーザー確認）。

- 保険証忘れ（ch=0のまま、金額は全部0）：ch=0なのでそもそも除外対象にならない。
- ch=1だが4項目すべて0円の行（例：赤阪さん）：除外される。
- ch=1だが保険負担計など一部が残っている行（例：納庄さん）：除外されない。

以前は「割合=交の行を除外」「4項目のうちレセ負担金だけ見て0なら除外」等、色々な条件を試して
何度も揺れ戻した。最終的にこの「ch=1 AND 4項目全部0」がユーザー確認済みの正解。
同じ「修正日報」という名前でも、`/daily_summary/detail`の「修正日報のみ」フィルタ（ch=0の行を
残す、同じ意味）とは別実装なので、修正日報関連のバグ調査では両方を確認すること。

## 施術者別月次

/staff/office/store_daily_report/daily_summary/monthly-print の施術者別日報集計は、店舗選択で絞らない。
その先生が対象月に担当した全店舗分を対象にし、日付・担当者IDで1日1行に集計する。

- 人数: 患者No の重複除外数。
- 自費: teacher.先生別外 = 0 の teacher.自費。
- 保険人数: teacher.請求金額 + teacher.保険負担 が 0 ではない行数。
- 保険負担: teacher.保険負担 の合計。
- 請求金額: teacher.請求金額 の合計。

2026/05 038 は店舗混在で対象にしつつ、日付単位で1行にまとめる。

## 日報集計一覧のサマリー編集

/staff/office/store_daily_report/daily_summary の一覧では、日報集計サマリーのうちレセコンとレジだけを直接編集できる。
保存時は dbo.T_日報集計 の対象行に対して、レセコン・レジのみ更新する。

- 月次処理済みの月は編集不可。
- 確定済み日報は、入金確認権限がない場合は保存不可。
- 先生別計、差額、銀行預入金額など他項目はこの一覧保存で更新しない。

## 日報詳細・患者別編集パネルの入力可否

/staff/office/store_daily_report/daily_summary/detail の患者別編集パネル（一覧の「+」で展開する
フォーム）は、2026-08-20のユーザー要望で入力可能な項目を絞った。入力欄（`input`/`select`/
`textarea`）を残すのは以下だけ。

- レセ負担金（＋負担金ch チェックボックス）
- 保険証グループ：割合・保険証区分（持参/忘れ/回収）・回収日
- 日報備考

それ以外（日別順・日付・時刻・新患・患者名・保険請求・差額）はinput要素自体を置かず、
`{{ }}`または`<span>`によるテキスト表示のみにする。手入力できない項目だと画面から
ひと目でわかるようにするため（`readonly`のinputで一度試したが、見た目が入力欄のままで
分かりにくかったためinput自体を外す方式に変更）。

- 保存側（`dbo.T_患者名日報`更新部分）も、表示専用にした項目（時刻・新患・患者名）は
  `update()`の対象キーから外し、既存値をそのまま残す。リクエストに値が来ていても
  更新しない（フォームにinputが無いので通常は来ない）。

### 保険請求・差額の計算式（2026-08-20訂正）

最初「保険請求はそのまま、差額＝保険請求−レセ負担金」で実装したが誤りで、正しくは
以下（8/3 ひなた・石田翼の実例で確認：請求金額1227・保険負担800・レセ負担金370 →
保険請求857・差額430）。

- 保険請求 ＝ 請求金額計 − レセ負担金
- 差額 ＝ 保険負担計 − レセ負担金

請求金額計・保険負担計は「その患者のその日の全先生別行（`T_先生別日報`）」の合計で、
`dailySummaryDetailSelects()`の請求金額計・保険負担計と同じ集計条件（`patient.保険証`や
`teacher.計算外`によるCASE分岐）を使う。1人の患者に複数の先生別行がある場合があるため、
今開いているパネルの1行分だけでなく必ず患者単位で合計すること（そうしないと同じ患者でも
どの行から開いたかで保険請求・差額の値が変わってしまう）。

- 集計ロジックは`patientReceiptTotals(患者No, 日付, 店舗)`に1本化。一覧表示時は
  `$patientDetailRowsByPatientNo`（既に取得済みの先生別行）をその場で合計して使い、
  保存時（`saveDailySummaryDetail()`）は同じメソッドで`T_先生別日報`を再取得して計算し直す
  （detail_rowsや保険証区分が同じ保存アクションで変わる可能性があるため、保存はdetail_rows・
  保険証の更新が終わったあとに行う）。
- 画面側はレセ負担金の`input`イベントで保険請求・差額欄（span）の表示を即時再計算するJSを
  入れているが、保存時はこのJS計算を信用せず、サーバー側で上記の式を計算し直してから保存する。
- 請求金額計・保険負担計そのものは画面から直接入力させない（先生別行の自費・保険負担・請求金額
  を編集した結果として決まる値のため）。

**表示は必ず保存値（2026-08-20、ユーザー指摘で修正）**：保険請求・差額欄の初期表示は
`$row['保険請求']`・`$row['差額']`（DB保存値）をそのまま出す。一度はパネルを開くたびに
PHPで計算し直した値を表示していたが、それだと保存値がズレていても画面には常に「正しく
見える」値が出てしまい、ズレに気づけなくなる（`docs/rules/00_global.md`の
「データと表示のルール」に書いてある2026年8月の給与差引支給額の事故と同じパターン）。
レセ負担金入力時のJSライブ再計算はあくまで「保存したらこうなる」というプレビューであり、
未編集時の初期表示は必ず保存値を使うこと。請求金額計・保険負担計のPHP計算（`$patientClaimTotal`/
`$patientCopaymentTotal`）はこのJSプレビューの基準値としてのみ使い、初期表示には使わない。

## 日報詳細ヘッダー保存

/staff/office/store_daily_report/daily_summary/detail の上部ヘッダーで編集できるのは、レセコン・レジ・表紙表示欄のみ。
保存で更新するのは dbo.T_日報集計 のレセコン・レジ・備考（表紙表示欄）のみ。

- 来院人数、予約人数、院内人数、先生別計、差額、交通事故、銀行預入金額、カード、誤差チェックは表示専用にし、この保存では更新しない。
- 表紙表示欄は dbo.T_日報集計.備考 に保存する。

## 日報詳細の「戻る」ボタン

`url()->previous()` は使わない。編集保存（+追加・一括ch等）はPOST→同じdetailページへのGETリダイレクトなので、
保存後は`url()->previous()`が月間一覧ではなく詳細ページ自身のURLを指すようになり、「戻る」が反応しなくなる
（Laravelの`StartSession::storeCurrentUrl()`はGETリクエストの度に「前回のURL」を現在のURLで上書きするため、
POSTを挟んでも保存直前のGET＝詳細ページ自身のURLが「前回」として残ってしまう）。
`route('office.store_daily_report.daily_summary', ['target_month'=>$targetMonth, '日報集計店舗'=>$targetStore])`
のように、遷移元が確定しているページでは明示的にルートを組み立てる（2026-08-18修正）。
同じ理由で`resources/views/staff_portal/admin/shift/basic.blade.php`（基本シフト）の「戻る」も同時に修正済み。
