# 管理者TOTP二段階認証（ローカルのみ有効化）

## 現在の状態

- `/admin/login` 用の追加実装。`/staff/login` の処理・パスワード保存方式は変更しない。
- `TCPGSYSTEM_DEV` は実運用の本番DB。専用テーブルの新規作成のみ明示承認を受けて2026-10-22に適用済み。既存テーブル・データは変更しない。
- ローカルの `.env` に `ADMIN_TWO_FACTOR_ENABLED=true` と `ADMIN_TWO_FACTOR_DATABASE_APPROVED=true` を設定した。既定値は両方false。
- いずれの設定も `APP_ENV=local/testing` の場合だけ有効。本番サーバーのコード・環境設定は変更しない。
- DBなしのHTTPテストでは、スタッフ認証を固定テストアカウント、2FA保存をメモリに置き換える。
- テスト中に `DB::connection()` を呼んだ場合はテスト失敗とする。マイグレーションは実行しない。
- ローカルで初回登録・認証をすると、専用テーブルにだけ登録・使用時刻・リカバリー消費の書込みが発生する。
- 本番サーバーへのコード反映は未実施。コミット・pushと本番反映は別途扱う。

## ログインの流れ

1. 従来のID・パスワード・管理者権限・退職判定を実行する。
2. 成功後は10分間有効の仮認証のみをセッションに保存する。管理者セッションはまだ作らない。
3. 未登録者には、アプリ内で生成したQRコードと手入力用キーを表示する。外部QRサービスは使用しない。
4. 6桁TOTPを確認してから初めて登録情報を保存し、管理者セッションを作る。
5. 初回は10個のリカバリーコードを保存確認後に管理画面へ進む。平文の再表示はこの画面を完了するまで。
6. 登録済みの場合はTOTP、または未使用のリカバリーコードを検証してログインする。

管理者ミドルウェアはスタッフIDと登録世代を照合する。既存の `admin_logged_in` フラグだけでは通過できない。
パスワード認証途中にも世代を記録し、TOTP検証・登録確定時に再照合する。
`/staff/admin-login` にも同じミドルウェアを適用し、2FA完了前の引継ぎを防ぐ。
一般スタッフのログイン処理・業務画面の計算やデータ処理には追加しない。

TOTPは6桁・30秒、前後1期間まで許容し、使用した期間以下のコードは拒否する。
コード入力は登録・通常認証・リカバリー共通でアカウントごとに1分5回、IPごとに1分30回。
パスワード認証のやり直しで試行制限は解除しない。
秘密鍵と一時表示用コードは暗号化し、DBへはリカバリーコードのHMACのみを保存する。
TOTPおよびリカバリーの消費は、承認後にSQL Serverで行ロックとトランザクションにより排他する設計。

## 専用テーブル（作成承認済み・適用済み）

対象DBは `TCPGSYSTEM_DEV`。次の専用テーブルだけを作成し、8列・主キー・作成直後0件を確認した。
既存テーブルへのALTER・データ移行・パスワード更新は行っていない。自動DDL・マイグレーションは追加していない。

```sql
CREATE TABLE dbo.admin_two_factor_credentials (
    staff_id NVARCHAR(50) NOT NULL PRIMARY KEY,
    secret NVARCHAR(MAX) NOT NULL,
    recovery_code_hashes NVARCHAR(MAX) NOT NULL,
    confirmed_at DATETIME2 NOT NULL,
    last_used_step BIGINT NOT NULL,
    auth_version CHAR(64) NOT NULL,
    created_at DATETIME2 NOT NULL,
    updated_at DATETIME2 NOT NULL
);
```

影響:

- 既存スタッフ情報には外部キーを付けず、既存データを変更しない。
- 有効化後に増える書込みは、専用テーブルへの登録、TOTP使用時刻更新、リカバリーコード消費のみ。
- 管理画面へのアクセス時に、専用テーブルの主キー検索が増える。
- 未登録の管理者はパスワード認証後に登録画面へ進む。過去の管理者セッションは再ログインが必要。
- 登録情報を紛失すると入れなくなるため、リカバリーコードの保管と復旧手順を有効化前に確認する。
- APP_KEYの変更・紛失は秘密鍵の復号やリカバリー照合へ影響するため、保全が必要。
- テーブルの存在・列定義とローカルLaravelからのSELECTは確認済み。SQL Serverの書込み・排他動作は、自動での書込みテストをしていないため未検証。

## 検証方法

```text
php vendor/phpunit/phpunit/phpunit --do-not-cache-result tests/Feature/AdminTwoFactorTest.php
```

実在する管理者のID・パスワード・TOTP秘密鍵はテストに使用しない。
自動テストはメモリの保存先だけで検証する。実アカウントの初回登録・実端末でのQR読取りは、利用者がローカルブラウザで操作する。

## ブラウザでの確認手順

1. `http://127.0.0.1:8082/admin/login` を開き、既存の管理者ID・パスワードでログインする。
2. 初回は認証アプリでQRコードを読み取る。アカウント名は `TCPG SYSTEM (Local)`。
3. 認証アプリの最新6桁コードを入力し「確認して登録」を押す。
4. リカバリーコード10個を安全な場所に保存し、保存確認にチェックして管理画面へ進む。
5. ログアウトして再ログインする。次回はQR登録ではなく6桁コード入力画面になる。
6. 直前に使用したコードは再利用できないので、同じ6桁が表示されている場合は次のコードに切り替わるまで待つ。

認証途中の有効期限は10分。5回試行した場合は1分ほど待ってからやり直す。

## 復旧の範囲

端末紛失時はパスワードと未使用リカバリーコードでログインできる。
認証アプリとリカバリーコードを両方失った場合は、サーバー管理者が本人確認後に専用CLIコマンドを使う。
Web画面からの初期化・2FA回避機能は追加しない。リカバリーコードの任意再発行UIは未実装。

```text
php artisan admin:2fa-reset 001 --reason="本人確認済み・端末とリカバリーコードを紛失" --dry-run
php artisan admin:2fa-reset 001 --reason="本人確認済み・端末とリカバリーコードを紛失"
```

上の `001` は例。実際の対象IDに置き換える。コマンドは実装のみで、実DBを対象には実行していない。

1. サーバー管理者が対象者の本人確認を行う。
2. `--dry-run` で接続先DB・対象ID・氏名・登録状態を確認する。
3. `--dry-run` なしで実行し、対象スタッフIDを手入力して確定する。理由は必須で、非対話実行は拒否する。
4. 対象者の専用テーブル1行だけを行ロックして、秘密鍵を空文字、リカバリー一覧を空配列、使用済み期間を0、新しいランダム世代に更新する。
5. 対象者はID・パスワードを再入力し、新しいQRコードと6桁コードで再登録する。新しいリカバリーコードも保存する。

登録行は削除しない。秘密鍵が空文字の行を「再登録待ち」として扱い、既存の `auth_version` を失効情報として残す。
列追加・テーブル追加は不要。`confirmed_at` は前回の登録確認日時を保持し、再登録成功時に更新する。
既に再登録待ちの場合も世代を更新するため、保持していた再登録画面は失効する。
専用テーブルに行がない未登録アカウントの場合は、初期化対象がないため変更しない。

ログイン済み・認証途中のセッションは世代不一致により次のリクエストで拒否する。
管理者認証情報が残る同一IDのスタッフセッションもチェックし、引継ぎ後の利用継続を防ぐ。
通常の `/staff/login` の処理は変更しない。他のスタッフIDの独立したセッションは初期化対象外。
セッションファイルやCookie自体の一括削除は行わず、保存方式に依存せずサーバー側で認証を失効させる。
既に認可済みで処理中のリクエストまで取り消すものではない。また、同じ世代照合を実装していない旧コードには効かない。

実行要求と結果は `storage/logs/admin-two-factor-reset.log` に記録する。
記録内容は対象ID・DB名・理由・OSユーザー・ホスト・イベントIDで、秘密鍵・認証コード・リカバリーコードは出力しない。
監査ログへの要求記録に失敗した場合は初期化しない。確認後に登録世代が変わった場合も初期化しない。
